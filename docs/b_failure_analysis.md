# Baseline B 계열(v1+) 실패 원인 분석 — 멘토 피드백 반영 1단계

> 멘토 피드백: "코드로 막자"가 아니라, 베이스라인에서 잘못된 답변이 **왜** 나오는지 먼저 분석하고
> RAG 개선 · 의도 파악 개선 · Tool calling 추가로 문제를 해결해 믿을 만한 결과를 내자.
>
> 분석 대상: `results/20261127-162737/runs.jsonl` 의 v1+ (공개 30문항 × 1회) — **3/30 통과, 27건 실패**
> 방법: 실패 27건마다 기대 도구(`expected.tool_calls`) · 실제 도구 호출 · 누락 문구 · 답변을 대조해 **첫 번째 원인** 하나로 분류

## 2. 해석

- **가장 큰 원인은 LLM의 판단이 아니라 "도구를 어떻게 쓰느냐"** 입니다 (① + ② = 16건, 59%).
  주문번호를 지어내거나, 조회 한 번 하고 멈춥니다. → 도구 설계·도구 설명·Agent loop 개선 대상
- **도구 자체가 없는 경우**도 3건입니다. 캡스톤 설계도(README)에 있던 도구를 구현하지 않은 것이 원인입니다.
- **규칙 해석 오류(④)는 2건뿐**입니다. 즉 "LLM 이 판정을 못 한다"보다 "판정에 필요한 정보를 못 가져온다"가 더 큰 문제였습니다.
  → 이전 결론("판정을 코드로 옮기자")보다 **도구와 조회 흐름을 고치는 것**이 먼저입니다.

## 3. 개선 순서 (원인 큰 것부터, 단계마다 측정)

| 단계 | 대상 원인 | 개선 (멘토 분류) | 측정 |
|---|---|---|---|
| 1 | ① 주문번호 추측 | Tool calling: 키워드로 주문 찾는 도구, 도구 설명에 "주문번호는 list_orders 결과에서만" | ① 8건 해결 여부 |
| 2 | ② 조회 후 멈춤 | Agent loop: 도구 결과에 상품 ID·클레임 여부 등 **다음 조회 단서** 포함, 프롬프트에 유형별 조회 순서 | ② 8건 |
| 3 | ③ 도구 없음 | Tool calling: `list_coupons`, `get_customer_profile`, 클레임 조회 구현 (설계도 기준) | ③ 3건 |
| 4 | ④⑤⑦ 해석·규칙·검색 누락 | RAG 개선(조항 단위 검색, 상담원 매뉴얼) · 반품 판정 도구 | ④⑤⑦ 5건 |
| 5 | ⑥⑧ 복합·되묻기 | 의도 파악: 요청 분해, clarify/confirm 규칙 | ⑥⑧ 3건 |

각 단계마다 공개 30 + 자체 검증 12 로 다시 측정해 "원인 X 를 고쳤더니 a → b" 를 기록합니다.
비교 기준: Baseline B(v1) · 현재 v1+ · 코드 우선 워크플로(v3, 90/90).

## 4. 1단계 결과 — 원인 ① 주문번호 추측 (`cs_agent/v4_agent.py`)

**추가로 찾은 근본 원인**: v1+ 가 추측한 주문번호 10건 중 5건이 `ORD-20261126-0001` 이었는데, 이건 **우리가 도구 설명에 적어 둔 예시 값**입니다. LLM 이 예시를 실제 번호처럼 베꼈습니다.

| 수정 | 내용 |
|---|---|
| A | 도구 설명에서 실제 주문번호·상품번호 예시 제거, "list_orders 결과의 값을 그대로(추측 금지)" |
| B | 없는 번호로 조회하면 오류 대신 **이 고객의 실제 주문 목록**을 돌려줌 (고객에게 되묻지 않고 바로 다시 조회하도록) |
| C | A 적용 후 새로 발견: 번호 **없이** 호출 → 프로그램 오류. 번호가 없어도 주문 목록을 돌려주게 함 |

측정 (공개 30 × 1회, 같은 모델·데이터): `results/20261128-111558/`(v1+ vs v4 A·B), `results/20261128-112118/`(v4 A·B·C)

| 지표 | v1+ | v4 (1단계) |
|---|---|---|
| 전체 통과 | 3/30 | 4/30 |
| 정답 문구 충족률 | 26% | 39% |
| 원인 ① 그룹 8건: 첫 도구가 `list_orders` | 0/8 | 5/8 |
| 원인 ① 그룹 8건: 이 고객의 실제 주문까지 도달 | 1/8 | 7/8 |

**해석**
- 원인 ① 자체는 대부분 해결됐습니다. 8건 중 7건이 **실제 주문을 찾아 들어갑니다.**
- 그런데도 통과가 1건인 이유는 **원인 ②(한 번 조회하고 멈춤)** 때문입니다. 주문은 찾았지만 반품 조건·설치 여부·클레임 상세를 이어서 조회하지 않거나, 018·026 처럼 목록을 받고도 "어떤 주문인지" 되물었습니다.
- 새로 보인 문제: 답변 중간에 **중국어로 바뀜**(009), 지명이 깨짐(022 "울릉도" → "ulcerdo"). qwen 모델의 언어 전환 문제로 별도 원인으로 기록합니다.

→ 다음은 **2단계: 원인 ② 조회 후 멈춤** (8 + ①에서 넘어온 6건).

**근거**: `list_orders` 결과에 클레임·설치배송 정보가 없어서, LLM 은 "더 조회할 것이 있다"는 걸 알 수 없었습니다.

| E | 시스템 프롬프트에 문의 유형별 조회 순서, "답하기 전 필요한 조회를 다 했는지 확인, '확인하겠습니다'로 끝내지 말 것" |

- **새로 실패: 004 · 014** — 둘 다 배송 지연 보상 문의. 2단계 전에는 `search_knowledge`(보상 정책)까지 갔는데 이번엔 배송 조회에서 멈춤. 1회 측정이라 흔들림인지 수정 영향인지 반복 측정으로 확인 필요.

**해석 — 남은 실패의 성격이 바뀌었습니다**
- 007 · 008 · 009 · 010 · 017 은 이제 **필요한 도구를 다 불렀습니다** (주문 → 반품 조건). 그런데도 실패하는 이유는 **반품 기한 날짜(예: 12월 1일(화))·기간 경과 여부를 LLM 이 직접 계산해야 하기 때문**입니다. 도구가 상품 조건(7일·30일)만 주고, 이 고객의 수령일 기준 기한은 주지 않습니다.
  → 원인 ④(규칙 해석)의 실체는 "LLM 의 판단력"이 아니라 **"도구가 판단 재료를 완성해서 주지 않음"** 입니다.
- 여전히 한 번 조회로 끝나는 케이스(003 · 006 · 020 · 022 · 023)도 남아 있습니다. 프롬프트 지시만으로는 이 모델(qwen2.5-14b)의 도구 연쇄 호출이 크게 늘지 않습니다 (평균 1.3 → 1.5회).

→ 다음은 **3단계: 없는 도구 추가 + 기존 도구가 판단 재료를 완성해서 돌려주게** (반품 조건에 이 주문 기준 기한·경과 여부, 쿠폰·적립금·등급 조회).

**지금까지의 결론 (1~3단계)**

## 12. 모델 교체 비교 실험 — "남은 실패가 모델 한계인가?"

| | qwen2.5-14b (제공 모델) | gemini-3.5-flash-lite |
|---|---|---|

**해석**
1. **우리 개선은 모델과 무관하게 효과가 있음**: 두 모델 모두 v1+ → v4 로 +9~10문항.

3. **그래도 모델만으로 해결되지는 않음**: 더 강한 모델의 v4 도 18/30 으로, 코드가 판정을 맡는 v3(qwen 으로 90/90)에 못 미침. 판정·필수 사실이 엄격한 상담에서는 **설계(코드 판정)의 효과가 모델 교체보다 큼**.
