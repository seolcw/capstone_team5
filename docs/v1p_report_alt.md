## 1. 한 줄 요약
Baseline B(v1)의 Agent loop 구조는 그대로 두고 **도구가 LLM 에 넘기는 정보를 코드로 검증**했더니,
악성 문서 지시 수용 **3/3 → 0/3**, 금지 표현(틀린 정책 안내) **3건 → 0건**, 공개 평가 통과율 **2/36 → 9/36**.
단, 엄격한 문자열 채점 기준으로는 아직 낮고 토큰은 약 2.8배 증가.

## 2. 무엇을 해결하나 (주제 PDF '운영 중 발생하는 문제' 기준)
| 영역 | 문제 | v1+ 해결 방법 |
|---|---|---|
| **지식 검색 — 정보 충돌** ⭐ | 과거 정책·미승인 문서를 참고 | 검색 결과를 승인 + 시행 중 + 공개용 문서만 전달 |
| 보안 — 간접 프롬프트 인젝션 | 문서 속 악성 지시대로 동작 | 위 필터로 REF-020 제외 + 문서를 '참고자료'로 감싸기 |
| 신뢰성 — 데이터 정합성 | 실제 배송 상태와 다르게 안내 | `현재_배송상태` = 택배사(shipments) 기준 |
| (2차 발견) 도구 선택 실패 | 도구를 아예 안 부르고 지어냄 | 첫 단계 도구 호출 강제, 도구 설명 보강, 텍스트 호출 복구, 오류 hint |

## 3. 구조
```
사용자 질문
   ↓
[입력 검사 guard]  ← 작업 1 (팀원 A, 아직 미구현 — 연결 자리만 있음)
   ↓
 LLM Agent  ⇄  [도구 결과 검증]  ⇄  정책 검색 / 주문 / 배송 도구
   ↓            · 문서 필터 · 참고자료 표시 · 택배사 상태 우선
 최종 답변       · 요일 계산 · 반복 호출 캐시 · NOT_FOUND hint
```

## 4. 개선 과정 (실패 → 수정)
1. **1차 (결과 필터만)**: 필터는 정상 동작(점검 10/10)했지만, 데모에서 LLM 이 **도구를 아예 호출하지 않는** 경우가 다수
   - 무료배송 질문: v1 은 중국어로 "300위안" 환각, v1+ 는 도구 호출을 본문 텍스트로 출력해 버림
   - 키보드 질문: 둘 다 주문 조회 없이 "주문번호 알려주세요"
   - → 필터는 **도구가 호출돼야** 효과가 있다는 걸 발견
2. **2차 (도구 호출 보강)**: 첫 단계 `tool_choice="required"`, 도구 설명에 '언제 쓰는지', 텍스트 호출 복구, NOT_FOUND 에 해결 방법,
   날짜·요일은 코드가 계산(`11월 30일(월)`)해 전달 → 아래 결과는 2차 기준

## 7. 트레이드오프
- **토큰 2.8배, 지연 +0.8초**: 도구를 실제로 부르고(0.5→1.2회) 결과·규칙이 길어진 비용. 대신 '지어낸 답'이 사라짐
- **답변 문장 일관성 하락**(10/12 → 7/12): 도구 결과가 길어져 문장 표현이 흔들림. 도구 순서는 대부분 일정(10/12)
- 필터가 너무 엄격하면 필요한 문서도 빠질 수 있음 → 내부용(MAN-001 등)은 상담원 연결 판단에 필요할 수 있어 고객 답변용과 분리 필요

## 8. 남은 한계와 다음 단계
1. **도구 선택은 여전히 LLM** — 지연 보상처럼 '추가로 정책을 찾아야 하는' 복합 상황에서 누락 (PUB-004)
   → 다음: 배송지연 결과에 관련 정책(CPN-004)을 도구가 함께 붙여 주기
2. **답변 형식 누락**(택배사명·주문번호·'배송완료' 단어) → 다음: 답변 규칙에 "주문번호·택배사·상태명 포함" 추가
3. **입력 검사(guard) 미구현** — 범위 외·직접 인젝션·타인 정보 요청은 작업 1에서 처리 예정
4. 평가셋 12건 기준 — 비공개 평가셋에서 재확인 필요
5. 취소·반품 '판단'은 v1+ 범위 밖 (v2 에서 코드로 처리)
